# 运行期主线覆盖

用户明确要求持续派遣或逐线覆盖时使用。普通一次性任务不建立执行表。原目标清单继续定义
用户要什么；本表只保存可由程序核对的工作包、代理活动和采用状态，恢复与钩子消费同一份表。
不能用已完成子切片或一个硬件缺口自动关闭整条主线。

## 启用与同源状态

插件的 `hooks/hooks.json` 声明运行入口。宿主必须支持这些事件，且该精确版本的钩子已被用户
审阅信任。安装成功、技能已读或脚本能单独执行，不证明钩子已生效；用宿主的 `hooks/list`
及真实触发回执核对。未信任时明确说明并继续可做工作，不自行改写全局信任记录。
未启用时按原有主线清单直接委派并核对原生状态，不把自动执行表登记或手工补录设为推进前置，
也不补造派发回执；实际钩子生效后再接入自动执行表。

钩子在明确持续请求时提供当前 `session_id`、实际数据目录和可执行命令。第一次按现有目标表
登记全部未交付主线，使用逐线持续模式保留整条成果和验收，工作包列下一核心成果或必要解锁；
不另抄完整业务合同，也不派人空等输入。逐线请求会自动选择连续模式；旧表缺少主线元数据时先补齐，不能沿用旧包状态绕过检查。
命令使用正式安装路径及该钩子给出的数据目录：

```powershell
py -3 -X utf8 -B "<插件根>/skills/lean-stack/scripts/coverage_runtime.py" plan `
  --session "<当前会话>" --cwd "<项目根>" --data-dir "<钩子数据目录>" --input "<计划JSON>"
```

计划形状：

```json
{
  "mode": "continuous",
  "goals": [{
    "id": "G01", "title": "原主线名",
    "outcome": "用户最终要使用的完整结果",
    "acceptance": "正式入口中能观察到的完成条件",
    "milestone": {"id": "M01", "title": "当前核心成果", "final": false},
    "work": [{
      "id": "W01", "title": "查清并实现当前核心成果",
      "kind": "core", "milestone": "M01"
    }]
  }]
}
```

后续计划更新保留未交付主线；新增切片属于原目标，不用删除旧行表示完成。主父负责登记，普通
子代理只完成当前卡，不改父执行表。状态命令使用同一会话标识与数据目录。
核心工作直接产生成果，必要解锁工作取得该里程碑必需的输入或决定性证据，辅助工作只服务这些结果。
辅助代理可以正常工作，但不能单独满足主线覆盖或完整交付。父代理须按实际消费者判断贡献，
不能把边缘整理改名为核心工作；程序不能替领域验收认证内容价值。旧的一次性包模式保持兼容。

## 实际派发与接续

计划为每个工作包给出执行者路径，例如 `/root/lean_g01_w01`。新派时把末段
`lean_g01_w01` 作为原生启动名称；业务消息正常携带任务卡、
身份、权限和完整业务上下文，无需手写关联标记。需要续用已有代理时，在该新工作包的计划中
显式分配已有代理的完整路径，再用该路径续派。
现有包尚在运行时不把同一执行者重复分给另一个就绪包；先采用返回结果，或选另一个执行者。

首派或续派无法以原生参数唯一对应一个就绪工作包时，在派出前拒绝，给出具体可用的
启动名称或目标路径和修正入口。程序按同一调用和真实成功路径关联当前包，不把计划或
失败调用算作运行。旧的唯一 `[lean-work G01/W01]` 调用仅作为兼容入口，不能越过显式分配。
原生唯一标识没有公开在普通回执中时不猜；成功派发先保留为已派待核对，由父调用原生代理列表的实际回执
确认对应路径仍在运行或已返回。子代理生命周期钩子属于子会话，不拿它伪造父会话的关联。
核对前不能直接等待，不能让历史线程永久冒充活动覆盖，也不因未知状态盲目重派。

工作包返回后由父核验，使用 `update --session ... --data-dir ... --input <动作JSON>` 采用：

- `{"action":"accept","goal":"G01","work":"W01","evidence":"实际验收收据"}` 只采用该包；
- 仍未交付则登记下一核心包并接续派发。核心阶段完成后更新同条主线的核心里程碑，
  保留旧包和证据；只允许尚无待派、正在执行或待采用核心包时前进，不覆盖在途工作；
- `{"action":"block","goal":"G01","work":"W02","blocker":"具体缺口","evidence":"来源"}`
  只阻对应包，核对同条是否仍有独立可做的研究、实现或验收；
- 逐线持续模式标明最终里程碑，完整结果实际验收后执行
  `{"action":"deliver","goal":"G01","milestone":"M02","evidence":"完整用户结果的交付收据"}`；
  当前最终里程碑须已有实际采用的核心成果，必要核心工作均已验收，不能只交辅助报告；
- 用户明确停止时 `{"action":"pause"}`；明确恢复原安排时 `{"action":"resume"}`。中断也保留表并暂停。

用户明确“回到三原则”时同样先暂停强制检查，保留未交付目标、证据和在途责任；
随后按入口默认三原则继续工作及动态增派，不能把暂停强制检查解释为停工。普通“继续”不自动
恢复旧强制模式，重新明确持续逐线安排后才恢复强制检查并核对实际状态。当前委派模式、来源、
覆盖范围、退出条件及各线下一核心动作应保留在既有项目当前快照，恢复不能只读旧人数或旧例外。

已有缺口解除后可 `retry` 对应包。命令只登记状态，不自行启动模型、操作设备或扩张权限。
局部包全部已验收或受阻时，未交付主线仍待接续：寻找可行路线、取得缺失信息、
排除操作异常本身都是可派的实质工作。确实整条受外部输入、权限或实际容量限制时，单独登记
`{"action":"block_goal","goal":"G01","blocker":"为何研究、替代路线及实现均暂不可做","evidence":"实际依据","resume_when":"最窄解除条件"}`。
有就绪、运行、待采用核心包或在途调用时不能整条暂缓；不得用整条阻断掩盖仍能进行的工作。
解除后用 `{"action":"unblock_goal","goal":"G01","evidence":"解除依据"}` 恢复，继续同一主线。
宿主已明确返回失败却没有发送后置回执时，可凭该错误用 `retry` 释放在途预占，再修正分配或重试；
尚未收到结果本身不算失败，不能用它解除实际正在执行的工作。
临时阻断可用同命令的 `--json '<动作JSON>'` 直接登记，不必先执行被守卫暂缓的文件写入。
宿主不能自动提供列表回执时，父先核对真实原生状态，再用
`{"action":"verify","goal":"G01","work":"W01","task_path":"/root/实际代理","state":"running","turn_id":"拒绝提示中的当前父轮次","evidence":"核查收据"}`
登记；`state` 也可为 `returned`，此时不需 `turn_id`。该路径必须匹配已经成功派发的工作包，不能用它补造派发或交付。

## 运行检查与边界

逐线持续模式的状态命令按主线编号返回待派、正在执行、待采用、待接续、待补主线信息、整条暂缓
或已交付，具体原始值见上表。没有下一核心包、只有辅助包或局部阻断时仍有逐线缺口。
已登记就绪核心包尚未派发时，前置钩子要求先派发，再执行受覆盖检查的局部工具或等待。
尚缺下一核心包时，等待与收口要求先接续；普通本地操作附上缺口提示，允许父推进其他无依赖主线，
不把一条局部缺口变成全项目工具锁。
派发、续做及执行表自身的纠错操作保持可用。子层不受父门约束。代理结束只进入待采用，不能
自动交付主线。父准备结束时仍有主线缺口，则 `Stop` 钩子要求同轮继续；其进度依据实际采用的核心成果，
改包 ID、换标题和辅助包交稿不重置同一缺口的防循环边界，仍未解决的缺口须显式呈现。

`SessionStart`（含宿主的压缩恢复入口）从同一执行表给出全部未交付项。真实输入、权限、账户或宿主容量阻断
仍按具体包报告，不能假装在运行，也不能为满足人数空占线程。表由实际消费者维护，不能证明
模型业务结论正确或自动发现所有潜在工作；领域验收仍沿用原消费者。
